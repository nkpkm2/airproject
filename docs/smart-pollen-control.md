# Pollen-aware smart control

## Purpose and operating boundary

The feature in the family overview is an opt-in advisory/actuation controller for Cupressaceae pollen (including cypress/Chinese arborvitae). It is paused by default. It only issues a physical power-button pulse or one mode-button pulse at a time after the device has a passed four-channel light calibration, an explicit weak-pollen baseline, and a fresh online state. Manual commands remain independent. Devices with unknown/contradictory lamps, no calibration, hidden catalog entries, or a stale heartbeat are skipped.

The current public pollen APIs have country/plant coverage limits: Open-Meteo's CAMS pollen fields are listed only for European pollen forecasts, while Google's country table lists China as grass-only and Japan as Japanese cedar/cypress. Neither can be treated as a Cupressaceae measurement in China. Weather is therefore only bounded contextual evidence. An operator can enter a local official level, expected peak time, and source URL. When the URL is HTTPS on a `*.gov.cn` domain, the local service also tries once per hour to read a small HTML page. It follows only government-domain HTTPS redirects, caps response size at 500 KB, and accepts only fresh pages with an explicit publication date, a Cupressaceae term, and a recognizable level/peak statement. An explicit peak date or date range near the cypress peak wording is preserved and displayed; its first date provides an estimated 10:00 local preboost start. This is an estimate, not an hourly pollen observation. The accepted level forecast is used for control for at most 48 hours; ambiguous, stale, unrelated, or unavailable pages remain visible as errors and do not override the operator setting. This is deliberately not a general-purpose scraper. Public Open-Meteo weather is fetched every 15 minutes after coordinates are configured and is attributed in the UI.

Social-data integration is intentionally not an unauthenticated scraper. The [Baidu Index help page](https://index.baidu.com/Helper) states that it has no open API and that the public edition does not support data downloads. The [Xiaohongshu scopes](https://openaccount.xiaohongshu.com/docs/scope) currently list only `basic_info` as open; `read_notes` remains planned, so that API cannot provide allergy-note search. The [Weibo Open Platform CLI](https://open.weibo.com/cli/quickstart) advertises search/research capabilities, but requires developer verification, OAuth authorization, and an activated trial or paid service. No account has been authorized and no paid service enabled for this household tool. Therefore social/allergy discussion remains a bounded, operator-verified input (12 points maximum, 12-hour expiry) until an account owner explicitly authorizes a compliant connector; it must never be mistaken for a species-specific pollen measurement.

## Inputs and score

The controller calculates an explainable 0–100 score:

- Official/local Cupressaceae forecast is primary: configured level 0/1/2/3/4 starts at 0/12/30/52/72 points.
- Current/forecast rain, temperature, relative humidity, cloud cover and sunshine can change the score by at most 12 points, but only when a local configured pollen season, fresh Cupressaceae forecast, or fresh operator-verified allergy trend provides pollen context. Weather alone outside those windows cannot raise the purifier tier. The weather request retains four past daily observations as well as the near forecast. Current precipitation is normalized using the API's backward-looking `current.interval` (usually 900 seconds for the current 15-minute model data) into an hourly intensity proxy; without a valid interval, no current-rain adjustment is applied. The provisional heuristic is: under 0.2 mm/h: no wash-off penalty; 0.2–1 mm/h: -2; 1–3 mm/h: -6; at least 3 mm/h: -10. Daily precipitation over 1 mm has a separate bounded -4 adjustment. These are cautious controller heuristics, not scientifically calibrated wash-off thresholds; they avoid treating trace drizzle as a strong wash-off event and avoid comparing accumulation totals across different time windows. Warm/sunny weather is a modest increase, low humidity adds at most a small dry-air signal, and a rainy previous day followed by warm sunshine gets only a +3-point contextual adjustment. A sunny streak is not treated as proof that pollen has been depleted; seasonal decline should follow local forecast/observations and the explicit indoor residual period. A Beijing-specific three-year study found temperature and falling humidity associated with pollen increases, while wind effects varied with dilution and local sources; therefore this generic controller does not award a positive wind-speed bonus without region-specific direction/source data ([study](https://pmc.ncbi.nlm.nih.gov/articles/PMC12019579/)). Relative humidity is read from the [Open-Meteo current/hourly weather API](https://open-meteo.com/en/docs); its docs specify that current precipitation is a backward-looking sum and expose the aggregation interval.
- Missing, malformed, boolean, or non-finite weather fields are treated as unknown, not as zero rain or clear skies; sunny-weather bonuses require the needed observations to be present. The six-hour outlook selects timestamped observations from the actual next six local hours (not the first six hourly-array entries, which are often already in the past).
- Rain weights remain provisional. A Beijing Cupressaceae study reported no significant daily-count effect from only 0.1 mm of rain on a peak day, while a León event study that included Cupressaceae found rain-event scavenging varied by intensity (its low-intensity group was below 1 mm/h, with stronger average scavenging in the medium/high groups). These results support treating trace rain differently from sustained rain, but the climate/site difference means those percentages are not transferred into this household's score; thresholds require local pollen observations to calibrate ([Beijing study](https://pmc.ncbi.nlm.nih.gov/articles/PMC12019579/), [León rain-event study poster](https://grupos.unileon.es/atmos/files/2022/11/2019_MEDPALYNO-Poster.pdf)).
- The six-hour risk explanation also reports sample counts for warm/clear, low-humidity, and high-rain-probability hours, so an operator can audit why the forecast score changed.
- Weather is polled every 15 minutes and is ignored after 60 minutes, or if its fetch timestamp is missing or more than five minutes in the future. A failed refresh may retain the last payload for diagnostics, but the timestamp guard prevents stale weather from affecting the score.
- Each weather payload is bound to the requested coordinates and timezone. Changing home location/timezone clears the cached forecast; a response that finishes after a location change is discarded, and the scoring function independently rejects mismatched location metadata.
- Social/allergy chatter adds at most 12 points. It cannot on its own produce a high or extreme decision.
- Configured annual local season adds 4 monitoring points only. It never claims that pollen was measured.
- An official expected peak within the configured lead window requests one extra tier of pre-ramp.
- The configured 17:10 window (40 minutes by default) raises the score to at least “normal.” If this schedule alone lifted a weak tier, it can end at its configured boundary; when pollen risk or the indoor-residual floor independently requires a higher tier, the ordinary 90-minute downshift dwell still applies.
- After high/extreme risk, a linear tail contributes up to 18 points over the configured indoor residual period (18 h by default). While that tail is active, it explicitly holds the target tier at least at normal even after its numeric score falls below the normal band; the timer is anchored to the last current/forecast high-risk sample, not to the hysteresis-delayed effective tier. Lower risk is accepted only after a 90-minute dwell.

Score bands are weak `<18`, normal `18–41`, high `42–67`, extreme `≥68`; weather/social/season alone are prevented from classifying extreme. Current score includes bounded weather suppression; the six-hour forecast tier may pre-ramp but is never allowed to lower today's tier. Upward transitions are immediate; downshifts wait 90 minutes. The outdoor pollen signal is not a direct indoor sensor, so results are recommendations, not medical advice.

## Fan target and physical actuation

Each selected purifier has a user-defined weak-pollen baseline (`off`, low, medium, high, auto). An `off` baseline is never automatically powered on. Explicit fan speeds scale only within low → medium → high; auto remains auto because its actual airflow is appliance-controlled and is not guaranteed to be higher. Controller aggressiveness limits the upward step: normal at most +1, high +2, extra at most +3 (bounded by high). Weak returns to the configured baseline.

The room estimate uses 160 m² × 2.5 m = 400 m³. With 23 devices and the supplied *nominal airflow* of 20/70/150 m³/h per device, aggregate estimates are 460/1,610/3,450 m³/h, or approximately 1.15/4.03/8.63 nominal air-volume turnovers per hour. 15× and 20× would require 6,000 and 8,000 m³/h. These are not CADR: filter efficiency, installation, leakage, and actual airflow are not known, so the UI explicitly avoids presenting airflow turnover as certified clean-air delivery. In addition to this full-fleet theoretical range, the live panel estimates the configured, calibrated devices' target airflow at the current tier and separates the currently online subtotal. Automatic mode remains unrated rather than being assigned an invented number.

For safety, the controller never sends a burst of mode taps. It queues at most one smart action for a device, durably checkpoints its intent before MQTT publish, waits for command acknowledgement and the expected lamp transition, then proceeds after a cooldown. If a mode does not change within 12 seconds during normal operation, it records the failure and retries cautiously; three consecutive failures pause that device until settings are saved again. If the service restarts while a physical pulse may be in flight, the result is treated as uncertain: it waits for a newer lamp report and never blindly replays that pulse. If no confirming state arrives, the device is paused for operator review. A manually issued MQTT command or an unexpected physical/other-controller lamp transition pauses automatic actions for that purifier for 30 minutes; expected transitions from the currently pending smart command are not mistaken for manual takeover. Power changes use the GPIO5 momentary pulse (300 ms), not a held optocoupler output.

## Settings required

1. Enter home coordinates and timezone for local weather context.
2. Enter the locality's cypress pollen season, official forecast level, source URL, and expected peak time when available.
3. Optionally enter a verified trend level and short evidence note from Baidu Index or public allergy reports; do not put account credentials here.
4. Set each commissioned purifier's weak-season baseline. Only calibrated devices can be selected for automatic control.
5. Choose normal/high/extra aggressiveness and review the capacity estimate before enabling.

## Validation and remaining integration

`test_smart_control.py` covers room-volume arithmetic, selected-device target airflow, calibrated/online capacity separation, location gating, evidence caps, rain effects, peak pre-ramp, target speed limits, government URL restrictions, fresh/old/missing Cupressaceae evidence, one-step physical actuation, and restart reconciliation of non-idempotent pulses. For the currently configured example (160 m² × 2.5 m, 23 units), rated airflow at high totals 3,450 m³/h, or 8.63 nominal air changes/hour. That is below a 15×/20× comparison target even before accounting for filter efficiency; actual CADR cannot be inferred without device test data. Firmware must be rebuilt and exercised on a bench before smart-control enablement on a real purifier. Baidu Index's official help page says it does not provide an open API; the current implementation intentionally accepts operator-verified social levels instead of scraping logged-in or unstable pages.
